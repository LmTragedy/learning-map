# Architecture decision — 2026-11-03

## Automatic note review — source-preserving suggestions

Keep the modular monolith, Markdown storage, CodeMirror editor and existing Codex adapter. Plate was assessed first: its suggestion marks and transforms operate on Plate/Slate nodes, while its Markdown integration converts between source strings and a structured value. Adopting that editing/suggestion stack would require replacing the current editing/undo/selection model and validating conversion of all existing notes. For this bounded feature, keep source text authoritative and add a small suggestion panel plus CodeMirror transactions. No editor or data migration is necessary.

The review endpoint receives the entire draft, optional named-note ID and displayed course revision, reuses scoped node/material/history context and structured Codex output, and returns at most three independently anchored suggestions. It never changes the course aggregate, saved notes, progress or Obsidian. The independent `note_review_model` defaults to `gpt-6-luna` with medium reasoning; tutor model/effort settings are unchanged. A bounded in-memory cache reuses separate review threads only for an unchanged draft hash, note identity, course revision, scope and model configuration; restore or any course change invalidates reuse, and tutor history is untouched. Model work runs outside SQLite transactions. At most two reviews run concurrently, with no overlapping reviews of the same note/node identity. Named notes must be bound to the current node. Citations must match real allowed material pages; unsupported or uncertain knowledge claims are labelled uncertain. Anchor positions are calculated by the server from unique original excerpts in UTF-16 units rather than trusting model offsets.

The client waits for a writing pause, checks the whole note, and invalidates a batch whenever text or context changes. Provider work is independent of saving. Each acceptance checks the complete source snapshot and exact range again, then uses one isolated editor-history transaction. Tab is intercepted only for a selected valid suggestion inside the editor or focused suggestion card; otherwise normal focus navigation remains. Failure pauses automatic requests until explicit retry. No native editor focus changes occur merely because a result arrives. Existing draft and save-conflict protection remains authoritative.

## Node personal notes — data protection

Keep the existing React/FastAPI/SQLite modular monolith and course aggregate. The note editor owns explicit user edits; the existing API client calls the personal-note route, which validates the node and compares the supplied original text inside `Store.edit` before saving the note and, when due, a pre-change snapshot in one transaction. Consecutive note-save backups are coalesced within ten minutes. A conflict rolls back both. Notes participate in existing course restart, snapshot, restore and local-trash behavior. A separate note database would duplicate data ownership and recovery. No model action or Obsidian adapter writes personal notes; accepted review suggestions become ordinary user-confirmed editor changes and use the existing save flow.

Browser drafts retain content and its original saved baseline under a unique editor key scoped to course and node. Writes happen during input, before UI navigation can unmount the editor. A page-local copy keeps edits and storage warnings available across node/tab changes if browser storage fails. Other windows' drafts are offered explicitly for recovery and are never overwritten or removed by this editor. Old plain-text drafts have an unknown baseline and require explicit version review. Refreshing saved content or recovering a draft never silently rebases it. A user-confirmed merge creates a new draft while retaining the original recovery copy; saving still performs the server comparison. Save acknowledgements update the submitted draft only and preserve later typing, including across component remounts.

The course-note list includes saved notes and recoverable local drafts, clears week filters when opening a node and permits editing mastered nodes. Out-of-scope review nodes require explicitly exiting review. An application-level close guard covers unsaved active drafts even when their editor is closed. Browser close prompts are best effort: forced termination or clearing browser storage can lose unsaved drafts. Successful saves persist to the course database; current editing also schedules autosave after 1.5 seconds. Conflicts pause autosave for explicit reconciliation.

The user clarified that a note belongs to the whole knowledge node and requested Obsidian-style live editing. The node-header action opens the learning workbench independently of learning tabs and mastery gates. Its note pane can sit beside a material page or saved lesson. Named notes use their own identity and may bind several nodes. Switching learning tabs keeps the note open; closing its pane retains the draft. Mobile uses the central document area rather than the dialogue sheet. Course/node IDs and `personal_note` storage are unchanged, so no data migration or Obsidian write is needed.

CodeMirror 6 owns Markdown parsing, text editing, selection, history and line wrapping. View decorations format headings, emphasis, inline code, quotes, bullets and links while retaining the original source; syntax marks reappear in the active paragraph. Source mode reconfigures presentation in the same editor, preserving its history. Display-only changes do not save or normalize text. Reading mode uses react-markdown and remark-gfm for full document rendering, including tables; live editing keeps complex table/image/HTML syntax as source. Reading mode sanitizes raw HTML and permits only the editor’s own color/highlight style values on span/mark elements; embedded images are placeholders with no automatic network fetch. Dependencies are locked and the editor is loaded on demand. Browser storage, note transactions and explicit user confirmation remain the same owners of draft and saved-state protection.

## Course goal dashboard — continuation

Keep the React/FastAPI/SQLite modular monolith and the existing map and course entry points. Goals belong to the course aggregate; optional fields allow legacy records to open without a migration. `goals.py` owns validated fields and the read-only evidence projection, `goal_routes.py` coordinates aggregate transactions and material extraction, and the board/editor/detail/candidate views use the existing API client and design tokens. A separate goal database would duplicate snapshot/restore ownership; auto-completing goals from nodes would violate explicit user confirmation.

Goal state and subtask checkmarks are user choices. Node learning and course-wide verification supply current evidence only; scope-only assessment and pending review are not counted as whole-node verified progress. Updates require the displayed revision, save a pre-change snapshot and reject stale writes. Candidate extraction reuses parsed material pages, the bounded material context, structured model replies and AI consent/settings. Model calls occur outside transactions, against all course materials even during PDF review. Candidates require valid course node IDs, existing pages and matching extracted quotes, but semantic accuracy still requires user review. Preview tokens bind immutable server-side candidates to the course revision and expire after 15 minutes. Explicit selection consumes the token and appends candidates in one transaction with a pre-import snapshot. Cancellation changes no course state. No rewards or new automatic learning rules are introduced.

Verify using real temporary SQLite/API flows for selection, revisions, source validation, status independence, scope progress, legacy editing and restart/restore; scripted model boundaries verify integration rather than model quality. Browser acceptance uses a separate synthetic course and database. The independent node-notes work remains in its own module and UI flow.

## Chinese understanding to simple English expression

Keep the modular monolith, existing UI, routes and state contracts. Share a teaching policy through the existing `SYSTEM` prompt used by node chat and structured model requests. Task prompts refine question orientation, Teach lessons and semantic assessment without adding a separate translation service or language mode. The alternative of a dedicated language-practice screen would duplicate history and require a new entry point; a stored English proficiency score would imply calibration that the application does not have.

The existing node context now supplies the active scope's last 30 messages and last three assessment text records to chat, questions, assessment and lessons, together with accepted course teaching preferences. Historical assessment attachments are not resent; the text evidence may be incomplete. Teach reuses this projection rather than duplicating historical payloads. Context limits reject oversized input instead of silently shortening answers. Strict PDF scope continues to filter before selecting recent records; no other node or PDF scope supplies learner evidence. Accepted profile advice remains explicit; no automatic proficiency inference or preference write is introduced.

The model first helps orient English material, uses Chinese for difficult reasoning and connects it to course terms and simple English, then leaves an opportunity for the learner's own attempt. Assessment uses the existing reasoning field to separate knowledge/logic, English clarity and harmless wording differences. Ambiguous meaning requires clarification through the existing uncertain result. Chinese correctness alone does not establish English proficiency. The application retains ownership of verification, ratings, snapshots and unlocks; chat, reading and term use do not change those records. Model calls stay outside transactions and existing node/scope conflict checks protect saves.

Verify real temporary SQLite/API flows, selected-source isolation, unchanged progress after teaching and reopening, judgment persistence and existing regression checks. Review actual model output separately using explicitly synthetic English database material; scripted responses verify integration and state rules, not teaching quality or long-term learning.

## Knowledge relationships — incremental extension

Keep React Flow, the existing node detail dock and the modular monolith. Extend the course-owned edge records with an explanation, usage conditions, evidence classification and page references, uncertainty, user confirmation and two directed difficulty estimates. Old edges receive read-time defaults; no destructive migration is needed. General relationships do not create prerequisite gates. Existing node IDs, prerequisites, conversations and progress remain authoritative.

Simple relationships open in the existing detail area. A complex relationship creates an ordinary synthesis node with related-node and relationship IDs, so Teach lessons, conversation, questions, assessment and scoped progress remain owned by the existing learning services. Switching presentation retains any synthesis node and its history. Identical relationships can be reused; different evidence or explanations must survive as separate records. Model estimates remain explicitly unvalidated. User edits and confirmation are explicit, revision-checked actions rather than automatic calibration.

The alternatives were a separate relation database and learning subsystem (duplicate ownership and restore complexity), and treating every relation as a node (unnecessary map growth). Neither is needed for this extension. SQLite aggregate edits and snapshots are atomic; model calls remain outside transactions. Relationship context and the related learner state must participate in stale-result checks. Strict PDF review excludes relationships whose complete evidence or related endpoints fall outside the selected sources; filtering only citations would leave cross-material claims in the prompt. Brief foundation detours keep the current review selection and offer a return to the original node.

Verify with copied synthetic database course PDFs, real temporary SQLite, model-boundary tests, a separate live-model dataset and browser interaction. Cover clickable explanations and source pages, synthesis learning/assessment, uncertainty labels, actual relationship use in tutor output, presentation changes, stale requests, restore/restart and unchanged original progress. This does not establish educational effectiveness or a calibrated difficulty formula.

## PDF review scope

Keep the modular monolith and existing course aggregate. A validated course-owned selection stores enabled state, PDF IDs and an AI context mode. A pure review policy module owns matching and scope identity. Graph generation always sees all course materials. Prerequisite/completion projection runs on the full graph; the UI then filters membership and permits temporary review entry without persisting unlock changes. Multi-source nodes match any selected PDF; unreferenced nodes do not match.

Strict mode filters source pages and context-bearing records and omits the merged node summary from model prompts. Its stable key hashes sorted immutable PDF IDs/hashes. Node conversations and questions are separate per key, while chats, attempts and immutable lessons append with a scope tag. Legacy records remain intact. The client receives an active-record projection with archived counts; exact Recall still exposes all raw history, while synthesis uses the scoped subset. Returning to course mode permits the original full context. Course title, node title, whole-node self-mark and course-wide verification metadata, explicit user input, answer attachments and accepted teaching preferences remain available as learning background, not PDF source evidence. Source filtering controls application inputs rather than guaranteeing model knowledge or output correctness.

Strict assessment passes and user resolutions write scope-specific verification, preserving course-wide mastery and unlocks even after leaving review. Self-marking remains an explicit whole-node user choice. Record-ID operations reject other scopes during strict review, including historical lesson reads; exit or return to the original scope to access them. All selection and record writes use existing SQLite transactions; model requests run outside them and revision-checked saves reject concurrent selection changes. Native Codex metadata remains an external side effect. Restore clears both normal and scoped thread references to avoid future hidden history. No material files are changed or removed. Verify with real copied synthetic PDFs/SQLite/restarts, captured external-model prompts, stale-result rejection and browser selection/exit checks; scripted model responses do not verify real model quality.

## Learning route and Teach lessons — approved extension

The user approved a main learning route with collapsible stages and node-local HTML lessons. Keep the modular monolith. A pure route projection groups consecutive prerequisite depths into stages; it does not rewrite prerequisites, node IDs, or completion rules. All prerequisites, including multiple parents, remain required. The full graph and temporary direct entry remain available. Alternative choices were layout-only cleanup (insufficient guidance) and a forced linear dependency chain (incorrect prerequisites).

The bundled Matt Pocock Teach skill is used as teaching instructions by a dedicated lesson service. Existing node goals, material references, actual conversations and assessment evidence replace Teach's separate workspace files. The model returns a structured HTML fragment and a check question. The application sanitizes the fragment, renders a shared self-contained HTML document, and stores immutable lesson versions inside the existing course aggregate. The adapter instructs the model not to use tools and rejects tool/approval requests, subject to the existing Codex protocol limitations described below. HTML uses an empty iframe sandbox and a restrictive document CSP; generated scripts, styles, links and external resources are not accepted.

Only explicit lesson actions call the model. Reopening uses saved HTML; reading a lesson never passes or unlocks a node. Supplementary lessons append within the node. Generation happens outside a transaction, followed by revision-checked save and a pre-change snapshot in the same transaction. Restoring a course includes its lessons; legacy courses need no migration. The application is the sole owner of progress. Main-route stages are navigation groups, not claims of a verified curriculum. Node splitting is not automatic.

Verification: legacy-state preservation, multi-parent ordering, malformed graphs, sanitization, idempotent lesson creation, model failure, concurrent edits, restore/restart, saved lesson display with AI disabled, stage collapse and temporary direct entry. Use isolated data for tests and keep a SQLite backup before changing the running application.

## Constraints and choice
New, local-first single-user application. No existing application or tests in the workspace. Preserve the supplied requirements notes and imported originals. Use a modular monolith: React/React Flow view → localhost FastAPI application → course domain policies → SQLite and immutable copied files. Document parsing and Codex app-server are outbound adapters. No cloud database, embeddings service or automatic Obsidian write.

The alternative of extending all of DeepTutor v1.7.1 was inspected: its learning policy is relatively isolated but LearningService owns a different SQLite schema and the API lifespan starts the full application container, migrations and provider/background services. Running that stack solely as a map API would create two owners of course state. NSA SkillTree similarly introduces Java/PostgreSQL and organization identity. React Flow owns graph rendering; existing parsers own PDF/OCR complexity. Our application owns the specific self-mark/assessment/feedback/recovery rules.

## Ownership and transactions
SQLite owns one JSON aggregate per course, a revision number, and full-course immutable snapshots. Each course has an independent directory of immutable material and answer copies. Application mutations read, validate and update in one SQLite `BEGIN IMMEDIATE` transaction. AI/parsing runs outside the transaction, then compare the revision; concurrent changes reject the result rather than overwrite progress. Map generations keep every existing node ID/progress; new nodes append. Map replacement/edit operations require preview and explicit confirmation if they change structure. Every map application snapshots the full course beforehand.

Restore saves the complete current course before replacing the aggregate. Files remain immutable and retained so both old and restored snapshots resolve their source and answer references. The learning profile is derived from active course aggregates; restore therefore restores that course's conversations, attempts and ratings together. Global preferences are separate explicit user choices.

Deletion uses a revision-bound preview token, shows all affected state, and marks the entire course aggregate as local trash in SQLite, retaining its immutable course directory rather than touching originals. Obsidian reads only configured vault Markdown; a write uses a content/target-bound preview token, refuses overwrites and writes only after explicit confirmation. External folders are never silently created or deleted.

## AI and failure behavior
Codex app-server uses persisted independent node thread IDs, read-only sandbox, a dedicated empty working directory, and rejects approvals/tool attempts. Local state is authoritative; prompts include the current saved history, so a restored course never relies on newer hidden thread history (restored thread IDs are cleared). Parsing/OCR output always carries page provenance and uncertainty. No model means explicit unavailable behavior; manual learning/marking, sources, Recall and feedback remain usable. No canned AI success.

Conversation names and course group labels are computed by the application and passed to the Codex adapter as metadata, never inferred from arbitrary model output. Metadata calls are external side effects and cannot join the course SQLite transaction; failures are surfaced, and titles may already have changed if a later operation fails. Course aggregates retain thread references. Native Codex sections and desktop sidebar section preferences were verified to have different IDs and one-way mapping; native grouping is not advertised as automatic desktop sidebar organization.

Recall synthesis uses a frozen node-history snapshot, validated structured output and message-ID/role checks. It rejects stale course revisions before recording the request's Codex thread reference. It does not change messages or mastery evidence. UI labels every synthesis item as AI-generated and displays the cited exact messages; citation checks do not establish semantic entailment.

## Defaults and verification

Initial difficulty is an explicitly labelled estimate. Recall defaults to exact stored messages, not invented summaries. No automatic difficulty or teaching adjustments. UI is checked in a browser; real model and parser tests are labelled separately from boundary fakes.
