# Architecture decision — 2026-11-03

## Visuals in future Teach lessons — 2026-11-03

Keep the same lesson transaction and isolated HTML. New requests use `VisualLessonDraft` with bounded declarative visuals. The application automatically attaches node-source excerpts and page references, and supplies up to six distinct original PDF/image pages to the model. The context identifies which pages were supplied; redraws may cite only those pages, within the active node and review scope. Source names, quote matches, uncertainty, visual IDs and numbering are application-owned. Source examples retain the exact extracted quote, original figures retain page pixels, and AI redraws or invented diagrams remain separate provenance values. Generated diagrams accept only bounded box/cell/text/arrow/line/point primitives. Lesson HTML, visuals and the result receipt commit together through the existing course edit.

Existing lessons are not rewritten. Pending receipts replay their exact saved prompt/schema against the saved raw reply; the schema selects the original text-only or new visual contract. Original text-only receipts do not gain newly inferred visuals during recovery. New receipts also retain the set of original image pages supplied for validating later recovery. Invalid visual output remains in the raw receipt and does not save a partial lesson. The alternative of a second automatic generation would add provider work and split result ownership, so visuals share the original lesson response.

## Saved lesson source visuals — 2026-11-03

Keep the existing modular monolith, course aggregate and isolated lesson HTML. The explicit lesson `visuals/recover` action reads the saved lesson's citations and existing material pages; it does not call a model or read a provider turn. It appends bounded, deterministic source-excerpt and original-page records to `lesson.visuals`. An optional explicit same-material page sequence provides a process view of existing material pages, rather than a newly drawn diagram. The UI renders these records outside the lesson iframe and derives image URLs from the current course, material and page. A Radix dialog portal keeps the focus view usable when task banners or a narrow workbench leave too little pane height. Quote matching compares whitespace-normalized extracted text only; it does not certify the original image or its meaning, and extraction uncertainty stays visible.

The service validates course revision, lesson review scope, material ownership and page existence before saving; PDF/image page cards also require an existing original file. A pre-change snapshot, lesson metadata and any already-verified lesson receipt projection are updated in the same SQLite transaction. Original HTML, raw provider replies and learner records remain intact. Deterministic IDs make repeated attachment a no-op. The alternatives were browser-only visual state (lost on refresh) and regenerating lessons (does not reuse the existing result). Verify source-page PNGs and course/receipt metadata after restart, plus stale revisions, scope rejection, repeat recovery and zero provider calls.

## Durable AI receipts and recovery

Keep the React/FastAPI/SQLite modular monolith. An independent SQLite AI task ledger owns request identity, the frozen local input, native thread/turn identity, received protocol events, complete raw replies and processing failures. Course snapshots remain the owner of learning content, not provider receipts. Alternatives were browser-only pending state (lost on refresh) and storing raw replies in course versions (validation rollback and restore would also lose or replay receipts). Neither meets recovery requirements.

The use case prepares a receipt before sending. The native adapter persists thread identity and events through an observer; the send-intent commit precedes the provider write. A lost acknowledgement remains unknown and never authorizes another turn. The complete reply is committed before schema validation or rendering. The existing business use case validates and applies it using `Store.edit(task_id=...)`; course edits, backup and the applied marker commit atomically. Model work and native metadata calls stay outside database transactions. Metadata failure has its own receipt field and can be retried without generation. Requests and raw replies stay under ignored local data, never in public logs or documentation.

Request IDs identify actions rather than equal prompts. Callers without an action ID receive a fresh identity. Unresolved work blocks an unrelated new action in the same logical scope rather than silently adopting its request ID. Automatic note review retains its explicit settled-receipt policy for an unchanged draft/scope/model. Reading/recovering a task uses only `thread/read` and saved raw replies. Explicit regeneration requires a fresh action ID; retries with that ID reuse the new task. Recovery compares saved context; read-only note checks compare the actual node/source projection, scope, restore epoch, model and named-note binding, allowing unrelated autosaves. Existing use-case checks plus immutable material/scope/restore-epoch checks protect course application. This deliberately prefers retaining a conflicting result over guessing a rebase. Restore atomically supersedes outstanding tasks and creates a new epoch; applied receipts remain deduplication evidence and never replay into the restored course.

Current-relation backfill is separate from the existing bounded course batch. Historical bridge receipts must match exact course/node/relation identities and original provider turn evidence; a matching title is insufficient. Historical import retains each provider turn separately, even if two turns answered the same batch. Import and formal application are distinct operations; a historical result for another batch cannot repair the currently open relation.

Verification uses temporary databases, scripted provider boundaries and protocol fixtures for duplicate submissions, received-but-not-applied failures, lost completion notification, restart, original tasks still running, context/scope changes, restore, exact bridge targeting and metadata failure. No new real model generation is needed for these checks. The existing live service is not replaced by this development task.

## Persistent conversations and inspectable legacy results — 2026-11-03

The independent `ai_conversations` table selects a thread by stable course/target, logical channel, strict PDF scope, restore epoch, explicit main-conversation generation and adapter/model identity. Chat and Teach lessons share the node learning channel. Questions and assessment share a separate assessment channel; note checks are separate per named note, and Recall has its own channel. Maps, bridge batches, goals and main lines use distinct stable course channels; retell uses its line identity. Titles remain display metadata. Thread-open events bind the directory before `turn/start`; business failure does not lose the thread. SQLite ownership prevents concurrent actions from sending into the same logical conversation. Unconfirmed turns retain ownership; rejected requests without a recorded send can release it. Effort changes alone do not split a conversation.

Explicit main-conversation reset retains all saved chats and lessons and changes only the current node/scope learning generation and legacy thread reference. Application and recovery check that identity again inside the course transaction. A short OS file lock spans the sending observer and actual protocol write, and also guards reset/restore. It does not span model waiting or a database transaction around provider work. Lock contention before the sending observer is a proven-unsent rejection; the original request evidence is retained and the claim is released. An uncertain transport after the send remains unknown and is never automatically retried.

Legacy scanning is an explicit local action, limited to the exact AI workspace, bounded rollout records, exact thread/turn identity and terminal-message evidence. Node/source or full-material identity supplies course binding; titles alone do not. Duplicate courses remain ambiguous. Generic legacy records are inspection-only, with the original output and current-object comparison retained independently of application. Recall/line/retell legacy requests lacking reliable course evidence are not automatically imported. A lesson fragment is compared with its saved page through the same renderer. Existing bridge content is compared before recovery: identical content is reported as already present; different content is a conflict, never a successful no-op application.

Each new applied receipt stores its result object and a typed `result_ref` atomically with the business result. Availability is checked against the current object, scope and restore epoch; raw output remains readable when availability is false. Old receipts without a reference require original-output evidence before a current object is verified. Native section IDs are stored separately from desktop section IDs. Desktop membership is only a dated observation supplied through supported desktop tools; no runtime desktop synchronization bridge is available to this service. Native metadata success cannot confirm desktop membership. Health captures a source fingerprint, process ID, start time and recovery contract at application creation.

## Automatic note review — source-preserving suggestions

Keep the modular monolith, Markdown storage, CodeMirror editor and existing Codex adapter. Plate was assessed first: its suggestion marks and transforms operate on Plate/Slate nodes, while its Markdown integration converts between source strings and a structured value. Adopting that editing/suggestion stack would require replacing the current editing/undo/selection model and validating conversion of all existing notes. For this bounded feature, keep source text authoritative and add a small suggestion panel plus CodeMirror transactions. No editor or data migration is necessary.

The review endpoint receives the entire draft, optional named-note ID and displayed course revision hint, reuses scoped node/material/history context and structured Codex output, and returns at most three independently anchored suggestions. It never changes the course aggregate, saved notes, progress or Obsidian. The independent `note_review_model` defaults to `gpt-6-luna` with medium reasoning; tutor model/effort settings are unchanged. An independent persistent review channel reuses its thread across draft edits and restarts, keyed by node, named note, scope, restore epoch and provider/model identity; tutor history is untouched. Durable receipts validate the actual source context and current note binding on both application and reuse. Unrelated personal-note autosaves do not invalidate those inputs. Model work runs outside SQLite transactions. At most two reviews run concurrently, with no overlapping reviews of the same note/node identity. Named notes must remain bound to the current node. Citations must match real allowed material pages; unsupported or uncertain knowledge claims are labelled uncertain. Anchor positions are calculated by the server from unique original excerpts in UTF-16 units rather than trusting model offsets.

The client waits for a writing pause and checks the whole note. Its receipt identity includes the draft, note, scope and independent review model, but excludes autosave revisions and UI correlation IDs. The request sends the displayed scope/model for server verification before work; omitted fields remain compatible with legacy callers. Existing marks map across unrelated edits rather than being discarded on every keystroke. Editing a marked excerpt or joining its word boundary drops that mark. Old asynchronous responses cannot place their offsets into a newer draft. Scope, note and model changes clear current suggestions. Provider work is independent of saving and remains serialized across draft edits because cancelling client waiting cannot cancel paid provider work. Each acceptance rechecks the original at its mapped range, then uses one isolated editor-history transaction; rejected transactions do not record acceptance or expose earlier user edits to suggestion undo. Tab accepts only a selected valid suggestion in the editor; Escape closes its card. The compact list supports keyboard navigation and reveals the existing editor when locating from reading mode. Failure pauses automatic requests until explicit retry. No native editor focus changes occur merely because a result arrives. Existing draft and save-conflict protection remains authoritative.

## Node personal notes — data protection

Keep the existing React/FastAPI/SQLite modular monolith and course aggregate. The note editor owns explicit user edits; the existing API client calls the personal-note route, which validates the node and compares the supplied original text inside `Store.edit` before saving the note and, when due, a pre-change snapshot in one transaction. Consecutive note-save backups are coalesced within ten minutes. A conflict rolls back both. Notes participate in existing course restart, snapshot, restore and local-trash behavior. A separate note database would duplicate data ownership and recovery. No model action or Obsidian adapter writes personal notes; accepted review suggestions become ordinary user-confirmed editor changes and use the existing save flow.

Browser drafts retain content and its original saved baseline under a unique editor key scoped to course and node. Writes happen during input, before UI navigation can unmount the editor. A page-local copy keeps edits and storage warnings available across node/tab changes if browser storage fails. Other windows' drafts are offered explicitly for recovery and are never overwritten or removed by this editor. Old plain-text drafts have an unknown baseline and require explicit version review. Refreshing saved content or recovering a draft never silently rebases it. A user-confirmed merge creates a new draft while retaining the original recovery copy; saving still performs the server comparison. Save acknowledgements update the submitted draft only and preserve later typing, including across component remounts.

The course-note list includes saved notes and recoverable local drafts, clears week filters when opening a node and permits editing mastered nodes. Out-of-scope review nodes require explicitly exiting review. An application-level close guard covers unsaved active drafts even when their editor is closed. Browser close prompts are best effort: forced termination or clearing browser storage can lose unsaved drafts. Successful saves persist to the course database; current editing also schedules autosave after 1.5 seconds. Conflicts pause autosave for explicit reconciliation.

The user clarified that a note belongs to the whole knowledge node and requested Obsidian-style live editing. The node-header action opens the learning workbench independently of learning tabs and mastery gates. Its note pane can sit beside a material page or saved lesson. Named notes use their own identity and may bind several nodes. Switching learning tabs keeps the note open; closing its pane retains the draft. Mobile uses the central document area rather than the dialogue sheet. Course/node IDs and `personal_note` storage are unchanged, so no data migration or Obsidian write is needed.

CodeMirror 6 owns Markdown parsing, text editing, selection, history and line wrapping. View decorations format headings, emphasis, inline code, quotes, bullets and links while retaining the original source; syntax marks reappear in the active paragraph. Source mode reconfigures presentation in the same editor, preserving its history. Display-only changes do not save or normalize text. Reading mode uses react-markdown and remark-gfm for full document rendering, including tables; live editing keeps complex table/image/HTML syntax as source. Reading mode sanitizes raw HTML and permits only the editor’s own color/highlight style values on span/mark elements; embedded images are placeholders with no automatic network fetch. Dependencies are locked and the editor is loaded on demand. Browser storage, note transactions and explicit user confirmation remain the same owners of draft and saved-state protection.

## Constraints and choice
New, local-first single-user application. No existing application or tests in the workspace. Preserve the supplied requirements notes and imported originals. Use a modular monolith: React/React Flow view → localhost FastAPI application → course domain policies → SQLite and immutable copied files. Document parsing and Codex app-server are outbound adapters. No cloud database, embeddings service or automatic Obsidian write.

The alternative of extending all of DeepTutor v1.7.1 was inspected: its learning policy is relatively isolated but LearningService owns a different SQLite schema and the API lifespan starts the full application container, migrations and provider/background services. Running that stack solely as a map API would create two owners of course state. NSA SkillTree similarly introduces Java/PostgreSQL and organization identity. React Flow owns graph rendering; existing parsers own PDF/OCR complexity. Our application owns the specific self-mark/assessment/feedback/recovery rules.

## Ownership and transactions
SQLite owns one JSON aggregate per course, a revision number, and full-course immutable snapshots. Each course has an independent directory of immutable material and answer copies. Application mutations read, validate and update in one SQLite `BEGIN IMMEDIATE` transaction. AI/parsing runs outside the transaction, then compare the revision; concurrent changes reject the result rather than overwrite progress. Map generations keep every existing node ID/progress; new nodes append. Map replacement/edit operations require preview and explicit confirmation if they change structure. Every map application snapshots the full course beforehand.

Restore saves the complete current course before replacing the aggregate. Files remain immutable and retained so both old and restored snapshots resolve their source and answer references. The learning profile is derived from active course aggregates; restore therefore restores that course's conversations, attempts and ratings together. Global preferences are separate explicit user choices.

Deletion uses a revision-bound preview token, shows all affected state, and marks the entire course aggregate as local trash in SQLite, retaining its immutable course directory rather than touching originals. Obsidian reads only configured vault Markdown; a write uses a content/target-bound preview token, refuses overwrites and writes only after explicit confirmation. External folders are never silently created or deleted.

## AI and failure behavior
Codex app-server uses persisted independent node thread IDs, read-only sandbox, a dedicated empty working directory, and rejects approvals/tool attempts. Local state is authoritative; prompts include the current saved history, so a restored course never relies on newer hidden thread history (restored thread IDs are cleared). Parsing/OCR output always carries page provenance and uncertainty. No model means explicit unavailable behavior; manual learning/marking, sources, Recall and feedback remain usable. No canned AI success.

Conversation names and course group labels are computed by the application and passed to the Codex adapter as metadata, never inferred from arbitrary model output. Metadata calls are external side effects and cannot join the course SQLite transaction; failures are surfaced, and titles may already have changed if a later operation fails. Course aggregates retain thread references. Native Codex sections and desktop sidebar section preferences were verified to have different IDs and one-way mapping; native grouping is not advertised as automatic desktop sidebar organization.

Recall synthesis uses a frozen node-history snapshot, validated structured output and message-ID/role checks. It rejects stale course revisions before recording the request's Codex thread reference. It does not change messages or mastery evidence. UI labels every synthesis item as AI-generated and displays the cited exact messages; citation checks do not establish semantic entailment.
